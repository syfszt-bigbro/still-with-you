# 产品决定记录

## 2026-10-28：公开发行的定位

**问题**：现有私人桌面陪伴原型如何变成任何人都能安装、又不会泄露原人物隐私的程序？

**用户决定**：允许建立公开 GitHub 仓库；保留现有桌面互动、计划、计时、运动、聊天、记忆、备份等能力；增加照片导入与动作形象生成；结合 ex-skill 的人物与关系记忆逻辑；上传内容不得包含原私人原型的任何隐私；公开后必须重新下载并从零复现。

**决定**：

- 中文产品名为“她一直都在”，英文名为 “Still With You”，仓库名为 `still-with-you`。
- 首版沿用现有原生 macOS 14 / SwiftUI + AppKit 架构，优先 Apple Silicon。
- 私人照片、聊天、口述、人物资料、API Key 和生成形象只保存在用户本机。
- GitHub 只发布源代码、原创中性占位角色、虚构示例、测试和构建说明。
- API Key 存入 macOS 钥匙串；备份不包含密钥。
- 所有可能产生费用的模型调用必须由用户主动触发并在界面中说明；离线计划、计时、互动、导入和本地动作形象生成仍可用。
- 公开前必须完成敏感词、密钥、高熵字符串、媒体和绝对路径扫描；随后从 GitHub 干净克隆，重新测试和构建应用。

## 2026-10-28：继承 ex-skill 的部分

参考来源：[therealXiaomanChu/ex-skill](https://github.com/therealXiaomanChu/ex-skill)（MIT）。

保留并产品化以下思路：

1. 先由 Persona 决定态度和说话方式，再按相关性选取 Relationship Memory。
2. Layer 0 硬边界：不替现实人物突然表白、道歉或作出原材料不支持的承诺。
3. 每条记忆保留来源；AI 总结与原始证据分开。
4. “她不会这样说”等纠正立即生效，并进入独立纠正层。
5. 追加聊天或照片只做增量合并；每次人物/记忆更新都生成可回滚版本。

不直接继承的部分：

- 不把星座、MBTI 或依恋标签自动当成事实。
- 不把整份聊天记录塞进每次模型请求。
- 不允许公开仓库、日志或崩溃报告携带私人资料。
- 不用模拟强化执念，也不把陪伴者描述成现实人物本人。

## 2026-10-28：视觉方向

主题是“被一段关系改变过，但仍然向前”。界面避免纪念馆式沉重，也避免粉色恋爱模板。

- **夜航墨** `#272838`：主文字与桌面角色阴影。
- **余光蓝** `#5D7DA6`：主要操作和记忆连接线。
- **晨光杏** `#F2B278`：完成、温度和“向前”的提示。
- **薄雾纸** `#E7EBEF`：原生窗口背景。
- **苔绿** `#7A9275`：本地保存、隐私安全和完成状态。
- **校正红** `#B55252`：纠正、删除与错误状态。

标题使用系统宋体，正文使用苹方，时间与来源使用 SF Mono。唯一的视觉签名是一条“痕迹线”：它从导入材料开始，经过人物、记忆和纠正，最后绕到桌面角色旁；不是装饰，而是显示每一步资料如何成为可追溯的陪伴。

## 2026-10-28：历史原文、说话人确认与语音

**问题**：导入聊天时强制生成总结会把推断伪装成事实；旧版还会沿用上一次的说话人映射。公开版的复刻声音入口也曾被错误简化为只剩系统朗读。

**决定**：

- 历史原文与关系记忆总结分开保存。每次导入只新增、去重原文，不自动制造描述或总结。
- 旧有或用户创建的总结可替换、可删除；操作前保留可回滚版本，原文证据始终独立保留。
- 每次导入都重新列出本次记录中的明确说话人。AI 开启时最多检查 20 个候选、每人最多三条短样例，最终必须由用户确认。
- 确认结果写在本次原文上，不用一个全局名称覆盖全部历史。同一个人在不同文件中叫“她”“assistant”或昵称时可同时生效；等待确认的记录不参与人物口吻学习，重启后会继续要求确认。
- 手动重新识别只追加新的历史名称，不抹掉已经确认过的别名；要改正单个文件时可重新导入该文件并重新确认。
- 无明确说话人字段时，不猜测双方身份；原文仍可保存与搜索。
- 语音保留两条路径：免费的 macOS 系统朗读，以及用户自备百炼 API Key 和音色 ID 的复刻声音。
- 公开仓库不携带私人音色 ID 或密钥；云端语音失败时自动回退系统朗读，文字功能不受影响。

## 2026-10-28：WeFlow Markdown 导入修正

**问题**：通用“姓名：内容”解析器会把 WeFlow Markdown 的文件头、引用与链接标题误当成说话人；不同会话内同时同文的消息也可能被误去重。

**决定**：

- 在通用 Markdown 解析之前优先识别 WeFlow，仅将 `## 日期 时间 说话人` 视为消息边界。
- 每条 WeFlow 原文保留会话 ID 与消息序号；去重时不会将私聊和群聊中的独立消息混为一条。
- 文件选择器允许一次导入多个文件；任一文件无效时整批不落盘，避免半成功状态。
- 说话人确认窗口提供“取消并撤销本次导入”，只删除本次新增的原文，不影响以前记录。
- 验收使用 6,476 条群聊与 4,314 条私聊导出：合计 10,790 条全部保留，候选仅包含 5 个真实说话人；再次导入后总数不变。

## 2026-10-28：图片、Word 与 PDF 历史导入

**问题**：真实聊天资料不只来自结构化导出，也可能是聊天截图、Word 整理稿或扫描 PDF。只支持文本会迫使用户先手工转档，并丢失截图里左右双方的位置线索。

**决定**：

- 增加 JPG/JPEG/PNG/HEIC/TIFF、DOC/DOCX/RTF 与 PDF 导入；可与原有格式一起多选。
- 图片使用 macOS Vision 在本机 OCR。文字按版面标成“左侧”“右侧”或“历史原文”，最终仍由用户确认哪一边是对方。
- PDF 优先读取原生文字；没有文字层的页面转为本机图片 OCR。混合型 PDF 按页分别处理，最多 200 页。
- Word 使用 macOS 自带的 `textutil` 在本机提取正文。提取结果进入原有的明确说话人解析和确认流程。
- OCR 与文档提取不会调用用户配置的聊天 API，也不会上传文件。每个来源保留内容哈希与页码/片段序号，重复导入不会再次增加记录。
- 文字类文件上限保持 10 MB；图片、Word 与 PDF 上限为 50 MB，避免在主程序中无界处理超大文件。

## 2026-10-28：照片预览、取景与安全替换

**问题**：只显示“已生成”会让用户无法判断头像和动作卡是否合适；重新选择照片后立刻覆盖，也没有反悔余地。

**决定**：

- 选图后先显示真实头像取景与代表动作卡，不把抽象占位图当成照片效果。
- 用户可调整缩放、水平位置和垂直位置，满意后再确认生成；设置页也能重新打开上次取景继续调整。
- 新动作包先在隔离目录完整生成，成功后才原子式替换；取消或生成失败时保留当前动作包。
- 私人数据目录保留一份本机取景工作图和参数，便于再次调整；它不上传，也不进入导出备份。
- 从旧版本恢复且没有工作图时，不伪装成可编辑状态，而是提示重新选择原照片。

## 2026-10-28：人物描述必须在记录之后生成

**问题**：首次配置要求用户在尚未导入任何记录时凭空填写人物描述，会把用户的即时想象当成人物事实，也颠倒了“证据 → 草案 → 确认”的顺序。

**决定**：

- 第一步只填写对方名字和对用户的称呼；不再展示或预填人物描述。
- 不冒充真人、不编造共同经历、不夸大关系等是固定系统边界，不要求用户重复填写。
- 导入历史后，必须先由用户确认哪一位说话人是对方；只有 `isCompanion == true` 的原话可以参与人物描述生成。
- 生成人物描述是独立、明确的付费 AI 操作。一次最多发送 120 条、共 24,000 字的已确认对方原话抽样，不上传整份资料库。
- AI 只输出人物描述草案；草案不会自动生效，也不会静默覆盖现有描述。用户必须在独立确认窗口中修改并确认。
- 没有 API 时仍可导入和确认记录，并可在设置中手动填写；人物描述为空时使用安全、简短、尊重边界的默认行为。
- 用户确认或手动修改人物描述前，自动保存上一版人物知识，继续支持回滚。
